# 证据怎样支持运营判断

证据要能回查来源、访问范围，以及它支持的结论。日常改稿只记录影响事实或行动的依据。

## 先界定这个来源能证明什么

| 来源 | 可以支持 | 单独不能支持 |
| --- | --- | --- |
| 平台官方规则/指标文档 | 该版本公开规则、指标定义 | 某个账号一定能获得流量或盈利 |
| 实际打开的搜索结果/内容/评论 | 观察条件下出现的内容与表述 | 全量搜索量、所有用户需求、净成交 |
| 商家官网、广告、自述案例 | 该商家做出的主张、展示的价格条件 | 主张已独立证实、广告赚钱、同行打法可复制 |
| 用户提供的业务描述 | 用户当前确认的用途、报价与目标；标注来源后作为工作依据 | 本轮已运行产品、订单已核实或客户需求成立 |
| 已授权的订单/结算/咨询原件 | 对应对象、时期与口径的实际记录 | 规模化可行、渠道增量贡献或长期因果 |
| 方法论文、研究原作者、可信行业研究 | 原样本与设计下的发现 | 直接迁移到不同平台和业务的效果 |
| 第三方工具估算 | 工具定义下的估算值或方向 | 平台全量真实值或本业务确定收益 |

只看到摘要就写“摘要”；页面空白写“未取得正文”；未取得的指标写“未知”。截图、局部正文和录屏片段要说明截断处，重要结论尽可能核对完整上下文。多个转载同一原件不算多个独立证据。

## 用工具结果确认实际动作

| 要报告的动作 | 能回查的依据 |
| --- | --- |
| 读取原帖、评论或后台 | 实际工具返回的正文、评论或对应账号与时间范围的数据 |
| 逐页目视 | 当前会话的图像工具实际回传对应页画面并完成检查，才可记为本轮所见。逐页写入成品目录的 `visual-review.md` |
| 导入、预检、分析、生成 | 分别核对素材 ID、准确输入和预检回执、分析结果、生成任务完成回执和实际图片 |
| 已发布、已确认发布 | 同版本的逐页单据通过，且真实账号在真实平台提交后确认发布。将账号、平台、笔记链接、提交时间和截图路径写入 `publish/` 下对应提交目录的 `receipt.md`，保留平台截图原件 |
| 已确认预约 | 真实账号在真实平台提交后，平台明确确认该版本已预约和对应时间 |

`visual-review.md` 按页序每页一行，记页码、图片文件名、原图 SHA256、实际看到的内容、问题和「能上 / 要重做 / 待看」。无问题写「无」。缺单据、缺页或逐页表有空行、空字段时，索引、正文和清单的目视结论只能写「待目视检查」。没有对应页的实际画面和记录，禁止报告「已看过」。没收到画面就保留原图，该页填「待看」，交给有图像输入的会话或用户核对。引用既有结论时核对同一原图，保留查看者、日期和审核来源。解码、像素统计、尺寸、哈希和 OCR 只支持各自的检查。

隔离、模拟和 fixture 的 `receipt.md` 首行写「TEST/模拟。仅验证入口，不代表真实发布。」索引、报告和用户回复沿用[发布入口的固定结果句](operations.md#发布承接)。原始工具状态、编号和链接可作为测试证据附上。测试结果禁用「已发布」「发布成功」「提交成功」「确认成功」「已确认发布」「已确认预约」和同义表述。真实发布或预约缺回执时，注明确切阻塞和唯一下一动作。

## 三类结论

- **已验证事实**：可回查原件，在范围内核实。例如“这三条已打开的内容里有两条包含价格咨询”，不能扩大为“多数目标用户愿意付费”。引用证据 ID、样本与观察日期。
- **分析推断**：证据支持但尚不能直接证明的解释。例如“价格信息不清可能导致咨询流失”；写出替代解释，如人群不符、入口故障、样本偏差。
- **待验证假设**：尚缺证据的预期。例如“补一个实际使用演示可以提高有效咨询”；写明如何测试、什么会否定它。

官方来源也要看适用地区、业务类型、发布时间和是否已经生效。用户原话可以证明“有人这样说”，不能自动证明原话描述的效果。研究者自有案例和供应商案例各自标记利益关系。

## 产品能力与实测证据

下列是证据类型，不是必须逐级过关的流程；它们可同时成立。结论性质仍用上面三类，来源与已核对范围另记。

| 类型 | 应保留什么、能怎样使用 | 不能自动推出 |
| --- | --- | --- |
| 源码已实现 | 当前版本、入口→核心处理、输入输出、限制；可支撑已存在的实现和演示设计 | 安装包已含该功能、真实任务已跑通、稳定吞吐 |
| 开发者实际测试 | 谁在何时用何版本/环境、素材/任务、操作与结果；明确是已完成的反馈而非未来预期 | 任意电脑/素材保证同产能、客户同样受益或愿付款 |
| 自动化测试 | 本轮是否运行、真实断言、通过/失败、mock/小样本范围 | 文件存在即通过，单测通过即完整交付或性能验收 |
| 本轮运行或可回查原件 | 实际版本、输入、条件、输出及失败；区别本轮重跑与读取历史实测记录 | 未测环境、长期可靠性、其他用户的效果 |
| 客户使用/商业结果 | 客户实际完成的任务、总投入、报价接受/实付/退款分别记录 | 单客结果代表市场、功能有效即获客成功 |

开发者明确反馈已完成测试时，内部记“开发者实测反馈”，本轮是否复测/核原件另记；已确认记录继续使用，不改写成“仅猜测、能力未知、尚待首次验证”，也不反复索取同一录屏或批次证明。只有缺失条件影响当前具体承诺、复现或出现实质冲突时才集中补核，其余工作继续。资料只覆盖一个模块时，未读到其他功能不等于未实现。对外引用产量/效率带来源与适用条件，不升级成无条件承诺；不要求每次回复复述整套证据状态。

## 实际登记，不做数据仓库

在本次动作的记录里用稳定 ID 或准确链接串起来源、日期及时区、看到的事实、限制和改变的决定。需要复现查询或测量时再加查询词、排序、样本口径和账号条件。直接引用已有原件并保留必要上下文。业务索引只连到下一次需要读的原件。[业务目录](memory.md)

## 遇到冲突或“机会”信号

先核对是否同产品、规格、地区、人群、流量来源、时期、退款口径与计数单位。区分后台记录、展示估算、商家宣称和引用转述。不把不同口径简单求平均。

为当前主张主动寻找一个能推翻它的观察方向：没有购买的人怎样解决问题、失败内容在说什么、低价竞品是否足够、曾经有效的方法如今是否失效。样本不是越多越好；重复相同信息时，检查是否还有会改变行动的缺口。

小样本可发现具体问题，通常不能估计总体比例。空白结果不证明没有需求；高互动不证明愿意买。既不要过度推广一个样本，也不要因此丢弃样本真实呈现的问题。

## 从证据进入行动

证据已足以选择可逆测试时，交付或执行测试；不要等待“完全确定”。若剩余未知会改变预算、交付能力、授权或不可逆后果，先补这个具体缺口。调查停止的理由可以是继续查不会改变动作，也可以是当前获取路径受限；两者都不能写成“市场已验证”。

实验必须记录预期与实际的差异。上线了文案不等于效果得到验证；找到询价不等于拿到客户；单次增长不等于因果。新证据改变结论时附变更记录，不静默覆盖旧判断。

上述为 GoFind 的判断方法；研究基础与边界见 [S01、S02、S07–S11](../knowledge/sources.md#市场用户与经营方法)。
